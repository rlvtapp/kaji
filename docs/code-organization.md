# Code organization guidelines

These rules apply to code written in this repository now, under Kaji, and after
any future product rename. They guide new work and incremental cleanup; they do
not require a mechanical rewrite of every existing file.

## Put each kind of file where a reader expects it

| Location | Contents |
| --- | --- |
| `crates/<crate>/src/` | Rust implementation modules (`.rs`) and no generated-language source templates. |
| `crates/plugins/<language>/templates/` | Source emitted into generated packages, grouped by runtime feature. Use the target language's extension (`.php`, `.ts`, `.go`, etc.). |
| `crates/plugins/<language>/tests/fixtures/` | Source compiled or executed only by generator tests, including probes. |
| `crates/inputs/<format>/tests/{fixtures,corpus}/` | Input samples and upstream corpora with their licenses and provenance. |
| `examples/` | Small runnable consumer projects, not generator implementation. |

A template that is valid source should retain its native extension. If its
placeholders make it invalid source, use `<name>.<language-extension>.tmpl` and
document the substitutions beside the renderer. Avoid `.txt` as a catch-all
suffix. Keep test probes out of production `src/`. Rust renderers may still use
`include_str!` to load a template from the crate's `templates/` directory.
When moving one, verify that `cargo package --list` includes it and that the
generated bytes or behavior remain correct.

Short generated snippets can stay in Rust when escaping and interpolation are
easy to review. Move a whole function, class, module, or runtime to a template.
Do not assemble a large target-language file through unrelated string
replacements spread across several Rust modules.

## Keep implementation files focused

- Aim for **200–300 lines** in a new production source file. At **400 lines**,
  split distinct responsibilities or record why keeping them together makes the
  code easier to follow. These are review prompts, not a CI failure for
  existing code, vendored inputs, generated output, or data fixtures. Reduce
  large existing files in focused changes rather than mechanically slicing them.
- Keep `main.rs` for process setup and dispatch, and `lib.rs` for the public
  surface and module wiring. Put argument parsing, configuration, compiler
  invocation, generation, and each command family in their own modules.
- In a language plugin, separate model rendering, operations, runtime code,
  pagination, package metadata, and test support when they grow independently.
  Do not create one-file modules solely to satisfy a line count.
- Put shared AST and plugin contracts in `kaji-core`; keep target-language
  rendering in its plugin crate. Inputs own parsing and their source-specific
  contracts. The CLI and Node addon compose those crates rather than becoming
  alternate implementations of the engine.
- Move a large inline test module into a neighboring `tests.rs` or an
  integration test. Keep tests near the behavior they verify, and compile or
  run representative generated output when a template changes.

## Refactor without changing generated output accidentally

Move one feature or one plugin at a time. First add or identify a focused test,
then move code or templates, and compare generated output before reviewing any
intentional behavior change. Preserve file ownership, regeneration, and
cross-language runtime tests. Run `cargo fmt --all --check`, the relevant crate
tests, and any generated-language smoke test touched by the move. Run the
workspace's `cargo clippy --workspace --all-targets -- -D warnings` gate before
merging Rust API changes. Keep output ordering deterministic, return actionable
errors at public boundaries, and use `Result` instead of panicking on invalid
user input.

The first cleanup candidates are `crates/kaji-cli/src/main.rs` (about 5,700
lines), `crates/kaji-cli/src/sdk_automation.rs` (about 3,300), and the Python,
Go, PHP, Java, and Elixir plugin `lib.rs` files (about 3,100–4,700 each).
Start template moves with one plugin, such as PHP, then apply the proven layout
to the other plugin crates. Existing upstream corpora already belong under
`tests/`; keep their original contents and provenance intact.
